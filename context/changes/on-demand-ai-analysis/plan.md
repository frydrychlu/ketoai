# On-Demand AI Analysis (S-09) Implementation Plan

## Overview

Implement FR-012: the user requests an on-demand AI analysis of their last N days of logged data (N ∈ {7, 14, 30}, default 14). The analysis identifies plausible causes of deviations from ketosis and **explicitly states its confidence level and data limitations** — hedging when the window is sparse. The result is a Zod-validated **structured** object, generated by a **blocking** request that reuses the proven OpenRouter boundary, rendered on a dedicated `/analysis` page, and **not persisted** (ephemeral, on-demand).

## Current State Analysis

- **The AI-on-Workers boundary is proven and retired.** `src/lib/services/macros.ts` and `src/lib/services/activity-estimate.ts` are two near-identical OpenRouter clients: `fetch` → `response_format: { type: "json_schema", json_schema }` → Zod-validate → retry-once (5xx only) → typed error class. S-09 reuses this exact pattern for a third, prose-heavy structured output. Key: `OPENROUTER_API_KEY` from `astro:env/server` (declared `optional` in `astro.config.mjs`); model `anthropic/claude-haiku-4.5`.
- **Four of the five range reads already exist.** `meals.listDailyTotals(supabase, from, to)` (`src/lib/services/meals.ts:49`), `activities.listDailyExpenditure(...)` (`src/lib/services/activities.ts:43`), `biomarkers.listReadings(...)` (`src/lib/services/biomarkers.ts:45`), and `profile.getProfile(supabase)` (`src/lib/services/profile.ts:9`). **The one gap:** wellness has only a single-day `getEntry` (`src/lib/services/wellness.ts:10`) — a range read must be added.
- **RLS scopes every query to the logged-in user.** The SSR client (`src/lib/supabase.ts`) runs as the authenticated user; no service passes an explicit `user_id` filter on reads. This structurally satisfies the FR-012 data-isolation guardrail ("analysis references only the requesting user's own data") — the aggregation cannot see another user's rows.
- **Page + island + API pattern is established.** `src/pages/history.astro` → `src/components/history/DayHistory.tsx` (client island fetching `/api/*` in parallel, spinner/error/render states) → `/api/*` routes. `/trends` and `/history` follow the same shape. `PROTECTED_ROUTES` in `src/middleware.ts:4` currently lists `/dashboard`, `/profile`, `/trends`, `/history`. Dashboard header (`src/pages/dashboard.astro:21-39`) holds the Trends/History/Profile nav links.
- **No `ai_analyses` table and no `lessons.md`.** Ephemeral output means no migration is needed for this slice.

## Desired End State

A signed-in user visits `/analysis`, picks a window (7/14/30 days, default 14), clicks "Analizuj", sees a loading state, and within ~10–30s gets a structured analysis: a short summary, a list of plausible causes (each with the evidence it draws on), a stated confidence level, and an explicit data-limitations note that reflects how sparse the window actually was. If the entire window has no data of any type, the page shows guidance to log more days instead of calling the LLM. An LLM failure shows a friendly Polish error. Nothing is stored; re-requesting regenerates.

**Verify:** with ~2 weeks of seeded data, request a 14-day analysis and confirm the four structured fields render and the confidence/limitations reflect the data density; with an empty account, confirm the "log more days" guidance appears and no LLM call is made.

### Key Discoveries:

- OpenRouter structured-output client pattern: `src/lib/services/macros.ts:56` (`parseMealToMacros`) and `src/lib/services/activity-estimate.ts:56` — copy the retry loop, `OpenRouterError` class, and `extractJsonObject` helper verbatim; only the prompt, schema, and return type change.
- Structured-output schema pattern: `src/lib/services/macro-schema.ts` pairs a Zod validator with a literal OpenRouter `json_schema` (`strict: true`, `additionalProperties: false`, all fields `required`). Mirror this for the analysis output.
- Range-read + JS group-by pattern: `src/lib/services/meals.ts:49` (`listDailyTotals`) — the wellness range read follows the same `.gte("day", from).lte("day", to).order("day")` shape (no group-by needed; wellness is one row per day).
- Client island pattern: `src/components/history/DayHistory.tsx` — `AbortController`, single loading flag, cleared state up front, Polish error copy, `localDay()` (duplicated by design, do NOT extract).
- Env + model constants live per-service; `OPENROUTER_API_KEY` may be undefined — services throw their typed error when it is (`src/lib/services/macros.ts:57`).

## What We're NOT Doing

- **No persistence** — no `ai_analyses` table, no migration, no analysis-history list/read endpoints, no revisiting past analyses. Each request is fresh and ephemeral.
- **No AI chat / follow-up questions** — one-shot analysis only (PRD Non-Goal, v2).
- **No export** of the analysis (PDF/CSV) (PRD Non-Goal).
- **No chart drill-down** or linking the analysis to specific trend-chart data points (PRD Non-Goal).
- **No streaming** — blocking request/response only; streaming on Workers stays un-attempted.
- **No free-form or slider N** — window is a fixed preset select (7/14/30).

## Implementation Approach

Build bottom-up in three phases, each independently type-checkable and lintable. Phase 1 lands the pure, testable data layer (the one new range read, the aggregation-with-coverage function, and the request/response schemas + shared types) with no I/O beyond existing reads. Phase 2 adds the OpenRouter client and the API route that orchestrates aggregate → empty-gate → call → hedge. Phase 3 wires the page, island, nav, and route protection. The FR-012 hedging guardrail is enforced two ways: (a) the server computes per-type day-coverage counts over the requested window and injects them as ground-truth facts into the prompt, and (b) the response schema makes `confidence` and `data_limitations` **required** fields the model cannot omit.

## Critical Implementation Details

- **Coverage is computed server-side, not inferred by the model.** The aggregation function returns, alongside the data, a small coverage summary (e.g. days-with-meals, days-with-biomarkers, etc. out of N). This is passed into the prompt as fact so the model hedges against real sparsity rather than guessing — directly addressing the PRD Socrates note on FR-012 (confident output on thin data).
- **Empty-window gate precedes the LLM call.** If coverage is zero across all types, the route returns a distinct "empty" response (guidance to log more days) and never calls OpenRouter — saving a wasted call and preventing hallucinated insight from nothing. A window with *any* data proceeds to the LLM and lets the hedging contract handle sparseness.
- **Prompt payload must stay bounded.** N is capped at 30 and biomarker/wellness are one row/day; meals/activities are pre-aggregated to daily totals before serialization, so the payload is at most ~30 compact daily records per type — well within token limits. Do not serialize raw meal/activity rows.

## Phase 1: Data aggregation layer & contracts

### Overview

Land the pure data layer the analysis needs: the one missing wellness range read, a function that assembles the N-day window across all types + profile and computes per-type coverage, and the request/response schema module plus shared types. No new I/O surface beyond existing service reads.

### Changes Required:

#### 1. Wellness range read

**File**: `src/lib/services/wellness.ts`

**Intent**: Add a `listEntries` range read so the analysis can pull a window of wellness entries in one query — the only missing range read among the five data types.

**Contract**: `listEntries(supabase: SupabaseClient, from: string, to: string): Promise<WellnessEntry[]>` — mirror `biomarkers.listReadings` (`src/lib/services/biomarkers.ts:45`): `.select("*").gte("day", from).lte("day", to).order("day", { ascending: true })`, RLS-scoped, returns `[]` when empty. No group-by (one row per day).

#### 2. Analysis request/response schema module

**File**: `src/lib/services/analysis-schema.ts` (new)

**Intent**: Single source of truth for the analysis output shape — the OpenRouter `json_schema` literal (what we ask the model to return) plus the runtime Zod validator (what we trust). Mirrors `macro-schema.ts`.

**Contract**: Export `analysisResultSchema` (Zod) and `analysisJsonSchema` (literal, `strict: true`, `additionalProperties: false`, all `required`). Fields:
- `summary`: string — 1–2 sentence overview.
- `causes`: array of objects `{ cause: string; evidence: string }` — plausible causes of ketosis deviation, each tied to what data supports it.
- `confidence`: enum `"low" | "medium" | "high"`.
- `data_limitations`: string — explicit statement of what the window lacked (the FR-012 hedge). Required and non-empty.

Also export the allowed window values as a const tuple `ANALYSIS_WINDOWS = [7, 14, 30]` used by the route's Zod schema and the island's selector.

#### 3. Aggregation-with-coverage function

**File**: `src/lib/services/analysis.ts` (new — service continues in Phase 2)

**Intent**: A pure-ish assembler that, given the supabase client and an N-day window, calls the four existing range reads + `listEntries` + `getProfile`, and returns both the per-day data and a coverage summary counting how many days in the window have data of each type. The coverage feeds the prompt's hedging.

**Contract**: `gatherAnalysisWindow(supabase, from, to): Promise<AnalysisWindow>` where `AnalysisWindow` (added to `types.ts`) holds: `profile`, `meals` (`DailyMacroSeriesPoint[]`), `activities` (`DailyExpenditureSeriesPoint[]`), `biomarkers` (`BiomarkerReading[]`), `wellness` (`WellnessEntry[]`), and `coverage` (per-type integer day-counts + `totalDays: N` + `hasAnyData: boolean`). Reads run in parallel (`Promise.all`). Window dates computed from N as ISO `YYYY-MM-DD`.

#### 4. Shared types

**File**: `src/types.ts`

**Intent**: Add the S-09 shared types under a new `// --- AI analysis (S-09) ---` section, per AGENTS.md (shared types live here, not in feature files).

**Contract**: `AnalysisWindow`, `AnalysisCoverage`, `AnalysisResult` (mirrors `analysisResultSchema` via `z.infer` re-export or a hand-written interface consistent with the codebase convention), and `AnalysisResponse` (the API's response DTO — a discriminated shape covering the analyzed result vs the empty-window case).

### Success Criteria:

#### Automated Verification:

- Type checking passes: `npx astro sync && npx astro check`
- Linting passes: `npm run lint`
- Build passes: `npm run build`

#### Manual Verification:

- `gatherAnalysisWindow` returns correct coverage counts against seeded data (spot-check via a scratch call or the Phase 2 route).

## Phase 2: AI analysis service & API route

### Overview

Add the OpenRouter client that turns an `AnalysisWindow` into a validated `AnalysisResult`, and the `POST /api/analysis` route that validates the window, aggregates, gates the empty case, calls the LLM, and maps failures to a friendly error.

### Changes Required:

#### 1. OpenRouter analysis client

**File**: `src/lib/services/analysis.ts` (extend from Phase 1)

**Intent**: Add `requestAnalysis(window: AnalysisWindow): Promise<AnalysisResult>` reusing the macros/activity boundary — OpenRouter fetch with structured output, Zod validation, retry-once on 5xx, typed `AnalysisError`.

**Contract**: Copy the `OpenRouterError` class, `delay`, retry loop, and `extractJsonObject` from `macros.ts`. Constants: same `ENDPOINT`, `MODEL = "anthropic/claude-haiku-4.5"`. Throw `AnalysisError` when `OPENROUTER_API_KEY` is missing or parsing fails twice. The **system prompt** (Polish, keto domain) must: instruct the model to identify plausible causes of deviations from ketosis from the provided daily data; require it to set `confidence` and write `data_limitations` grounded in the **coverage facts** included in the user message; forbid inventing data. The **user message** serializes the compact per-day data + the coverage summary. `temperature: 0`, `response_format` = `analysisJsonSchema`.

#### 2. Analysis API route

**File**: `src/pages/api/analysis/index.ts` (new)

**Intent**: The single `POST` endpoint. Validates N, aggregates the window, short-circuits the empty case, calls the LLM, and returns the structured result — following the auth/validation/error shape of `src/pages/api/meals/index.ts`.

**Contract**: `export const prerender = false;` + `POST: APIRoute`. Steps: 401 if no `context.locals.user`; 500 if no supabase client; parse body with a Zod schema requiring `window_days` ∈ `ANALYSIS_WINDOWS` (400 on failure); compute `from`/`to` from N and today; `gatherAnalysisWindow`; if `!coverage.hasAnyData` return `{ status: "empty" }` (HTTP 200) **without** calling OpenRouter; else `requestAnalysis` and return `{ status: "ok", result, coverage }`. Catch `AnalysisError` → 422 with a friendly Polish message (mirror meals' 422 at `src/pages/api/meals/index.ts:129`); rethrow anything else. Response DTO = `AnalysisResponse` from Phase 1.

### Success Criteria:

#### Automated Verification:

- Type checking passes: `npx astro sync && npx astro check`
- Linting passes: `npm run lint`
- Build passes: `npm run build`

#### Manual Verification:

- `POST /api/analysis` with `{ "window_days": 14 }` on a seeded account returns `status: "ok"` with all four result fields populated and coverage counts matching the data.
- The same on an empty account returns `status: "empty"` and makes no OpenRouter call (verify via absence of latency / logs).
- An invalid `window_days` (e.g. 10) returns 400.

## Testing Strategy

### Unit-ish / manual verification:

- `gatherAnalysisWindow` coverage counts are correct for: a full window, a window with gaps, and a fully-empty window.
- The empty-window gate prevents the OpenRouter call (the load-bearing cost/hallucination guard).
- Zod rejects `window_days` outside {7,14,30}.

### Integration (manual, local):

- End-to-end from the page against seeded data (`npm run seed:trends` / `seed:history` provide biomarker + multi-type history).
- Data isolation: since RLS scopes reads, a second account's analysis reflects only its own (empty) data — spot-check with a second local user.

### Manual Testing Steps:

1. Seed a local account with ~2 weeks of data.
2. Visit `/analysis`, request 14 days, confirm the four structured fields and that limitations reflect any gaps.
3. Request 7 days; confirm confidence/limitations shift with the narrower window.
4. Sign in as a fresh account; confirm the empty-window guidance.
5. Break the API key; confirm the friendly error path.

## Performance Considerations

- Blocking call is ~10–30s; the island shows a loading state throughout (accepted UX per plan decisions). No timeout tuning beyond the platform default.
- Payload is bounded: meals/activities pre-aggregated to daily totals, biomarkers/wellness one row/day, N ≤ 30 — at most ~120 compact records total. Do not serialize raw meal/activity rows.
- The empty-window gate avoids a wasted LLM call on accounts with no data.

## Migration Notes

None — the analysis is ephemeral; no schema changes. All reads reuse existing RLS-protected tables.
